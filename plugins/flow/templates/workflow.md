# Project Workflow

> 中文为正文语言，命令与术语保留英文。本文件是开发流程的**单一事实源**；项目特有的内容（单向门清单、
> 上线方式、命令、设计源）写在文末「项目补充 P1–P6」，正文里写「P1」「P3」即指那一节。
>
> 一句话：**按后果分级，以上线为终点。** 默认路径要快——小片、一次审阅、合并即上线、用户实测；
> 只有错了收不回来的改动（单向门）才放慢。
>
> 设计依据：DORA（小批量、主干开发、重审批不提升稳定性）、Amazon 单向门 / 双向门决策、Google 代码审阅
> 标准（让代码变好就批，不求完美）、Shape Up（胃口与断路器）、Anthropic Claude Code 最佳实践（给可运行的
> 验证；审阅者只报影响正确性的问题），以及 flow 0.1–0.4 在两个项目上的实测数据（审阅占 44% token、spec
> 首轮全 FAIL、上线后的问题 7/9 来自真实数据与产品理解而非代码逻辑）。

## §0 三条原则

1. **小片上线**：工作单元是一个能单独上线、用户能亲手用到的竖切小片，不是按层切的 phase。
2. **按后果分级**：错了能 revert 重发就没事的（双向门）快做；收不回来的（单向门）才走重路径。
3. **尽早碰现实**：真实数据、真实外部系统、用户实测，比对着 spec 和 fixture 反复推演更能发现真问题。

## §1 两种模式

- **讨论模式**：用户在问「怎么办 / 我要方案 / 先研究 / 一起想想」时进入。只调研、只出方案——可以读代码、
  看真实数据（只读）、查资料，**不改代码、不开分支、不写 spec**。先想清楚这笔需求背后的目的、谁在操作、
  系统该承担什么，再给方案；方案以 §3.1 的定形卡收尾。
- **交付模式**：用户对定形卡说「做」（或「按这个来」）之后进入，按 §3 走完到上线。

用户的话拿不准属于哪种 → 按讨论模式先给定形卡，不要先写代码。

## §2 两类门

**判据只有一个：这次改动如果错了，revert 重新部署能不能就没事？**

- **单向门**（不能）：会留下不可逆后果的改动。典型：动真钱的写路径（下单、撤单、止损、划转、支付）、
  账本与记账口径（错了会污染历史数据）、密钥与权限、改既有表列 / 数据迁移 / 删数据、审批与状态机守卫、
  对外发出就收不回的动作。本项目的清单见 **P1**。拿不准 → 按单向门。
- **双向门**（能）：其余一切——新页面、新表、只读接口、报表、文案、通知格式、内部重构等。

不按层数、文件数、行数分级。`.claude/flow.json` 的 `sensitive_paths` 只是机械提醒，判据是后果：
路径清单外的代码一样可能是单向门（例如后台任务里算净值的代码）。

## §3 交付流程

### 3.1 定形（每个需求一次）

写代码和 spec 之前，先出一张定形卡（`/flow:shape`），不超过 15 行：

```
目标：<用户的原话>
第一片做完你能：<一句话，用户能亲手做到的事>
这次不做：<明确的范围外>
胃口：<愿意花的时间，如 1 小时 / 半天；不是估算>
门：双向 ｜ 单向（<P1 哪一类>）
怎么验收：<上线后在哪里点、看到什么；或一条命令>
切片：<1–3 片，每片一句；后面的片可以等用户用过第一片再定>
```

- 只在「不问就会做错、且答案会改变实现」时提问，最多 3 问，用 AskUserQuestion 一次问完。
- 能看真实数据就先看（只读）：用户的真实账户、真实接口返回、线上日志，比推测可靠。
- 用户说「做」即开工；用户不在（无人值守）时由模型拍板，把假设写进 PR 描述。
- 范围只往小里定。审阅、实现中冒出来的新边界情况，先问「第一片没有它行不行」，行就记进「这次不做」。

### 3.2 切片

- 一片 = 一个 PR：非测试代码大约不超过 400 行，从入口到结果端到端可用（或藏在开关 / 未链接的路由后面），
  能单独部署。**不按层切**——「先 core 再 api 再页面」要等最后一层做完用户才看得到东西。
- 新能力的第一片先「走通骨架」：最薄的一条路径打通真实外部系统（只读 API、testnet、真实数据），
  让集成问题最先暴露。
- 分支只活几小时到一天；同时进行的片不超过 2 个。

### 3.3 实现（`/flow:build`）

- 在 worktree 里做；输入只有定形卡（单向门加 spec）。小片可以在当前会话做；大片或单向门交给一个干净的上下文（新 agent / 新 session），主会话只收结论。
- 计算、判定、状态流转、账务、鉴权、数据读写：先写失败测试再实现。纯展示改动不强制，附截图即可。
- 外部系统的 fixture 从真实响应录制（只读 key / testnet），不手写推测的格式和错误码。
- 完成前跑 **P3 的 check 命令**到全绿。与本次改动无关的既有失败：在主干上复跑确认后写进 PR 描述（P5）。
- 交付要带证据：check 的输出；改了 UI 的附一张截图。

### 3.4 审阅

| | 双向门 | 单向门 |
|---|---|---|
| 写代码前 | 不审 | `flow:risk-reviewer` 审定形卡 + spec 一轮 |
| PR 完成后 | `flow:pr-reviewer` 一轮（整个 diff、新上下文） | `flow:pr-reviewer` + `flow:security-reviewer` 并行一轮 |
| 复审 | 只复核未关闭的 BLOCKER | 同左 |

- **严重度按后果定，不凭感觉**：可能导致重复下单、裸仓、资金 / 净值 / 记账错误、数据丢失、告警静默失败、
  密钥泄露、越权的，一律 BLOCKER，不管看起来多「不太可能」。
- **只有 BLOCKER 挡合并。** 其余意见写进 PR 评论，作者自选；「测试没钉住」只有在单向门的核心不变量
  完全没有测试时才算 BLOCKER。
- 审阅结论（一行 verdict + BLOCKER 清单）贴成 PR 评论。审阅最多两轮，第二轮仍有 BLOCKER → §3.6 断路器。
- 审阅者被要求找问题就总能找到——追每一条会导致过度工程。不做变异分析，不审措辞与格式。

### 3.5 合并与上线（`/flow:closeout`）

- **双向门**：审阅无 BLOCKER → 由模型合并（`gh pr merge --squash --match-head-commit <审过的 sha>`）→
  按 **P2** 部署 → 冒烟检查 → 告诉用户去哪里试。
- **单向门**：PR 由用户合并。涉及下单 / 资金的，合并前在 testnet 或 dry-run 跑通（P2）。
- 合并后立刻清理：删远端分支、`git worktree remove`、`git branch -D`（squash 合并后只能 -D）；叠链 PR 先 `gh pr edit --base <主干>`。
- 用户试用的反馈就是下一片的输入。

### 3.6 断路器

出现任一情况就停下，带选项找用户（砍范围 / 给新胃口继续 / 放弃），不要硬推：

- 用时超过胃口的 2 倍；
- 审阅两轮仍有 BLOCKER；
- 同一个问题纠正了两次还不对（此时换干净上下文、带着教训重来，胜过继续修补）。

## §4 单向门的额外纪律

1. **spec**：定形卡之后写 `docs/specs/<名>.md`，不超过 150 行，只写不变量、资金 / 记账公式、失败模式
   （重试、并发、部分成功）、对外契约、明确不做。实现细节留给实现方，不要求逐条 `file:line`。
2. **写代码前审一轮**：`flow:risk-reviewer` 看定形卡 + spec；BLOCKER 修进 spec，除非需要重新设计，否则
   不再复审。
3. **测试先行且不被实现方改写**：核心不变量的测试由另一个 agent 先写好提交；实现方不改既有断言，确需改的
   在 PR 描述里单列理由；终审核对测试文件的 diff。
4. **PR 终审**：`flow:pr-reviewer` + `flow:security-reviewer` 并行一轮。
5. **用户合并**；涉及下单 / 资金的先在 testnet 或 dry-run 跑通。
6. 单向门同样要小片：把「钱怎么动」和「页面怎么显示」拆开，后者通常是双向门。

## §5 停点

需要用户的地方只有三处，其余决策由模型拍板，理由写进 PR 描述，**不问流程问题**：

1. **定形卡**：讨论 → 交付的切换。
2. **单向门 PR 合并**。
3. **上线后请用户试**。

另外两种情况也要找用户：断路器触发（§3.6）；需要用户才能做的事（凭据、生产权限、外部平台配置）。
**只要在等用户，就发通知**（PushNotification 或用户配置的渠道），不在停点上空等。

汇报用用户的语言：现在能用什么 / 哪里坏了 / 已修了什么 / 需要你做什么。不讲 phase、SHA、审阅轮次。

## §6 文档与状态

- **状态在 GitHub 和 git 里**：PR、issue、提交历史。不维护任务勾选、SHA 回填、track 登记、metadata、
  失败基线文件、阶段报告、交接文档。
- **PR 描述**：定形卡 + 做了什么 + check 输出 + 审阅 verdict + 怎么试 + 已知未做。
- **产品决策**（改变规则、口径、资金模型的）写 `docs/decisions/<YYYY-MM-DD>-<slug>.md` 一页，并同步修订
  上游设计文档。这是长期资产。
- spec 用完即弃：合并后不维护；行为的事实源是代码、测试和设计文档。
- 部署步骤变了才改 runbook。

## §7 教训与流程反馈

- **代码类教训**：能进 hook 的进 hook（`.claude/flow.json`；硬禁止用 `permissions.deny`）→ 只对某类文件
  成立的进 `.claude/rules/`（frontmatter 用 `paths:`）/ 领域陷阱进 skill → 最后才进 CLAUDE.md。
- **流程类教训**：用户对流程不满或流程出了错 → **当天改本文件**：所有项目适用的提到 flow 插件仓库发版，
  只属于本项目的写进「项目补充」。memory 只留指针，不留正文——写在 memory 里的流程规则，别的 session
  和 agent 看不到，等于没改。
- **度量**：定期跑 `/flow:stats`。目标：双向门当天上线；PR 中位数非测试代码 ≤400 行；每个 PR 审阅 ≤1 轮；
  只改文档的提交 <15%。感觉不可靠，看数。

## §8 分支与提交

- 主 checkout 只读，永远停在主干；一切改动走 worktree（flow 的 hook 会拦）。
- 动手前 `git fetch`，查有没有既有分支或已合并 PR 在做同一件事。
- conventional commit，描述用英文：`<type>(<scope>): <description>`，type ∈ feat / fix / docs / refactor /
  test / chore。
- 改项目自己的 hook / settings.json：它们锚定 session 启动目录，worktree 分支上的改动合并前不生效——在分支上
  手工喂 stdin JSON 验证（正例 + 反例），合并后第一个 session 复验。
