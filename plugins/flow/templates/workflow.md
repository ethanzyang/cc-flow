# Project Workflow

> 中文为正文语言，命令与术语保留英文。本文件是开发流程的**单一事实源**，也是 conductor 插件的执行规则：
> `/conductor:new-track` 按 §3 排 plan，`/conductor:implement` 按 §4 做每个任务、按 §5 收每个 phase。
> 项目特有的内容（单向门清单、上线、命令、设计源、失败基线）写在文末「项目补充 P1–P6」，正文里写「P1」
> 「P3」即指那一节。
>
> 一句话：**conductor 的「分诊 → spec → plan → 实现」骨架不变；流程重量按后果定，plan 按能上线的小片排，
> 一个改动审一次。**
>
> 设计依据：flow 0.1–0.5 在两个项目上的实测（审阅占子代理 token 44%、spec 首轮全 FAIL、记账 PR 占一半、
> 上线后的问题 7/9 来自真实数据与产品理解），以及 DORA（小批量、重审批不提升稳定性）、Google / Meta 代码
> 审阅（一个改动审一次）、Ship / Show / Ask、Amazon 单向门 / 双向门、Shape Up（胃口与断路器）、Anthropic
> Claude Code 最佳实践（给可运行的验证；审阅者被要求找问题就总能找到）。

## §0 原则与两种模式

1. **小片上线**：plan 的每个 phase 是一个能单独上线、用户能亲手用到的竖切小片，不按层切。
2. **按后果分级**：错了 revert 重发就没事的（双向门）快做；收不回来的（单向门，P1）才走重路径。
3. **尽早碰现实**：真实数据、真实外部系统、用户实测，比对着 spec 和 fixture 反复推演更能发现真问题。

- **讨论模式**：用户在问「怎么办 / 我要方案 / 先研究 / 一起想想」时进入。只调研、只出方案（可以读代码、
  只读地看真实数据），**不改代码、不开分支、不立项**；方案以分诊卡收尾。
- **交付模式**：用户对分诊卡说「做」（或「按这个来」）之后进入，按 §2–§5 走到上线。
- 拿不准属于哪种 → 按讨论模式先给分诊卡。

## §1 停点（只有 4 处）

| # | 停点 | 形态 |
|---|---|---|
| 1 | **分诊卡** | `/flow:triage` 输出，≤12 行；用户说「做」即开工，可逐项否决 |
| 2 | **需求访谈** | 最多 3 问，只问不问就会做错、且答案会改变实现的；AskUserQuestion 一次问完 |
| 3 | **立项确认** | 只有 track 才有：spec + plan **一起**给用户确认一次 |
| 4 | **三档 PR 合并** | 碰 P1 单向门的那一片，PR 由用户合并；涉及下单 / 资金的先在 testnet 或 dry-run 跑通（P2） |

- **上线后请用户试不是停点**：发通知告诉用户去哪里试，接着做下一片；用户的反馈是后面几片的输入。
- **只要在等用户就发通知**（PushNotification 或用户配置的渠道），不在停点上空等。
- 其余决策由模型拍板，理由写进 PR 描述，**不问流程问题**。用户不在（无人值守）时，停点 1–3 由模型按卡片
  拍板并把假设写进 PR 描述；停点 4 只能等用户。
- 汇报用用户的语言，三行：

```
现在能用什么：<按需求原话逐条对号；没做的写「未做」>
还缺什么：<下一片 / 无>
需要你做什么：<去哪里试 ｜ 合并 PR #n ｜ 跑这条命令 ｜ 无>
```

不讲 phase 编号、SHA、审阅轮次。

### 断路器

出现任一情况就停下，带选项找用户（砍范围 / 给新胃口继续 / 放弃），不要硬推：

- 用时超过胃口的 2 倍；
- 审阅复审后仍有 BLOCKER；
- 同一个问题纠正了两次还不对（此时换干净上下文、带着教训重来，胜过继续修补）。

## §2 分诊（`/flow:triage`）

### 2.1 三档：按后果和规模，不按层数

先判门：**这次改动如果错了，revert 重新部署能不能就没事？** 不能 → 单向门（P1 列了本项目的典型路径，
拿不准按单向门）。再看规模：一个 PR 做不做得完（非测试代码约 400 行）。

| | **一档** | **二档** | **三档** |
|---|---|---|---|
| 判据 | 双向门，一个 PR 做得完 | 双向门，要多片 | 单向门：动真钱的写路径、账本与记账口径、密钥与权限、改既有表列 / 数据迁移 / 删数据、审批与状态机守卫、对外发出就收不回的动作 |
| 入口 | `/flow:spec`；小 bug 走 D 车道直接修 | `/conductor:new-track` | `/conductor:new-track` |
| 产物 | `docs/specs/<x>.md` 一页 + 一个 PR | track：spec + plan（phase = 片） | track：spec（不变量 / 资金公式 / 失败模式 / 对外契约）+ plan + 先行测试（§4.5） |
| 审阅（§6） | 有逻辑 1 次；纯展示 / 文案 / 配置不审 | track 做完 1 次 | 写代码前 spec 1 次 + 每个单向门片合并前 1 次 |
| 实现 | 同会话 | 立项确认后同会话 `/conductor:implement` | 实现换干净上下文（新 session 或新 agent） |

- **文件数、层数不作判据**；视觉没定不升档，它决定要不要走设计环节（§3.2）。
- 三档 track 里的片也分门：只有碰 P1 的那几片按单向门审、由用户合并；页面、只读接口等其余片按二档走。
  「钱怎么动」和「页面怎么显示」拆成不同的片。
- 一档做着发现要多片，或碰到了单向门 → 停下改档，不硬塞进一个 PR。

### 2.2 车道（决定 spec 的形态）

| 车道 | 适用 | spec 写什么 | 验收 |
|---|---|---|---|
| **A 视觉不确定** | 新交互模式 / 要先看到长什么样才能定 | 设计包（§3.2）+ 行为 | UI 片按设计稿核对（`/flow:visual-verify` 模式①） |
| **B 功能调整** | 行为要变（含满足降级条件的新页面、UI 微调） | DELTA：现状 → 目标行为 → **明确不改** | 测试；UI 附截图 |
| **C 重构** | 行为不变，结构要变 | 不变量 + 先补钉住现状的测试 | 原有测试全绿；涉 UI 截图无差异 |
| **D 小 bug** | 单点缺陷 | 不开 track：复现测试（Red）→ 修（Green）→ 回归 | 复现测试转绿 |

D 车道纪律：先试一把全自动，连改两轮改不动就重开会话重述问题；发现是跨片、涉 schema 或类别性问题 → 改档开 track。

### 2.3 范围与拆分

- **分诊卡上写胃口**（愿意花的时间，如 1 小时 / 半天；不是估算）和「这次不做」。范围只往小里定：审阅、
  实现中冒出来的新边界情况，先问「第一片没有它行不行」，行就记进「这次不做」或 `conductor/backlog.md`。
- **能看真实数据就先看**（只读）：用户的真实账户、真实接口返回、线上日志，比推测可靠。
- **一个 track 内按片推进是默认**。只有需求里有两块能各自交付的东西时才拆成两个 track，拆之前必须答：
  「做完第一段，用户能亲手用到什么？」——答不出、或答案里没有需求原话的主入口 → 不拆。
- **拆了就同时立项**：两段都登记 tracks.md，后段描述行以 `⛔ blocked_by: <前段 track_id>` 开头（conductor 不解析它：
  `/conductor:implement` 自动选题时跳过前置未完成的条目；前段最后一片的 PR 删掉这个前缀）。后段 spec 引用前段
  的 FR，不重复采访。

## §3 Track 生命周期

```
分诊卡（停点 1）→ 访谈（停点 2，按需）→ [设计环节 /flow:design-track，A 车道]
  → /conductor:new-track：spec + plan → [三档：spec 审一次 + 写先行测试] → 立项确认（停点 3）
  → /conductor:implement：一片一片做，每片 实现 → check → PR → [三档单向门片：审 + 用户合并（停点 4）]
     → 合并 → 上线 → 请用户试 → 下一片
  → track 做完：审一次（§6）→ 收尾
```

### 3.1 立项（spec 与 plan）

- **spec** 不超过 200 行，引用上游设计文档的章节号，不复制正文。「逐字精确」只用于用户可见文案、资金 / 记账
  公式、对外契约；实现细节写「实现方自选」，不写成待定，也不要求逐条 `file:line`。三档的 spec 只写不变量、
  资金 / 记账公式、失败模式（重试、并发、部分成功）、对外契约、明确不做。
- **plan 的 phase = 片**：
  - 一个 phase 一个 PR，非测试代码约 400 行以内，从入口到结果端到端可用（或藏在开关 / 未链接的路由后面），
    能单独部署。**不按层切**——「先 core 再 api 再页面」要等最后一层做完用户才看得到东西。
  - 第一片先「走通骨架」：最薄的一条路径打通真实外部系统（只读 API、testnet、真实数据），让集成问题最先暴露。
  - 后面的片可以只写一句目标，等用户用过前面的片再细化。phase 多于 5 个说明该拆 track 或砍范围。
  - 每个 phase 末尾的 meta-task 照 conductor 格式写 `- [ ] Task: Conductor - User Manual Verification
    '<Phase>' (Protocol in workflow.md)`，含义按 §5 执行。
- **三档**：spec 写完派 `flow:spec-reviewer` 审一次（§6），BLOCKER 修进 spec；然后写先行测试（§4.5）。
- **立项确认**：spec + plan 一起给用户看一次（停点 3）。确认后：二档在同一会话直接 `/conductor:implement`；
  三档换干净上下文开工（§3.3）。
- **立项文件跟第一片走**：track 目录、tracks.md 登记都提交在第一片的分支上，随第一片的 PR 合并，不单独开立项 PR。

### 3.2 设计输入（Claude Design）

| 情况 | 设计输入 | 验收 |
|---|---|---|
| 新界面 / 新交互，视觉没定（A 车道） | **设计包**，由 `/flow:design-track` 在立项里出 | `/flow:visual-verify` 模式① |
| 新页面，满足下面三条降级条件 | spec 内嵌「结构清单 + 逐字文案 + 状态」 | 截图；需要时模式③ |
| 改既有界面的样式 / 布局 | 动手前截现状 | 截图对比；需要时模式② |
| 纯后端 | 无 | — |

- **新页面降级**三条同时满足：只用设计真相源（P4）既有 token 与组件语法；没有新交互模式（多步向导、拖拽、
  表单状态机）；结构与文案能在 spec 里逐字给出。分诊卡里写明降级理由。
- **设计包是立项里的一个环节**，`/flow:design-track` 跑两次：第一次写 BRIEF（输入材料 + 已核实的事实与硬约束，
  「设计只能在其中取舍」）推到用户的 Claude Design 让用户画；第二次把画好的包拉回、快照进 track 的 `design/`，
  接着出 spec / plan。**行为先冻结**的需求（账务也要收敛）：一个 track 里行为片在前，UI 片之前再按已冻结的行为
  出设计包（`--track <id>`）。
- **四件套**：`BRIEF.md`（输入材料表 + 约束）、`SPEC.md`（设计规格）、`INVENTORY.md`（功能穷举，**全部条目进
  验收标准**）、`DECISIONS.md`（编号决策，实现不得违反）；随附高保真稿与 `tokens.css`。快照入仓后只读（hook 强制）。
- 设计与业务规则冲突 → 列清单问用户（停点 2 的一部分），不自行折衷。
- 设计目录的多人协作与云端同步见设计真相源的 `SYNC.md`（`/flow:design push` / `pull`）。

### 3.3 Session 边界

- **二档**：立项确认后同一会话做完；上下文吃紧时 `/clear` 后 `/flow:catchup` 接着做。
- **三档**：立项与实现分开上下文（新 session，或派一个只拿到 spec / plan 的新 agent）——这同时检验 spec 能否独立
  执行，也让写先行测试的和让它们转绿的不是同一个上下文。
- 同时进行的片不超过 2 个；分支只活几小时到一天。

## §4 任务流（`/conductor:implement` 的 Task Workflow）

### 4.1 每个任务

1. **选任务**：按 plan.md 顺序取下一个可做任务。
2. **标记进行中**：`[ ]` → `[~]`（不单独提交）。
3. **写失败测试（Red）**：运行并确认失败后才继续（§4.2）。
4. **实现到通过（Green）**：最小实现让测试转绿。
5. **重构**（可选）：测试保护下清理，重跑保持绿。
6. **记录偏离**：实现偏离 `tech-stack.md` → 先更新文档（附日期说明）再继续。
7. **提交**：代码与 plan.md 的 `[x]` **同一个提交**；conventional commit（§8），描述用英文。

**不做**：逐任务 `git notes`、回填 SHA、单独的记账提交。想附说明写进 commit body。

### 4.2 Red 判定

编译失败与断言失败任一即为有效 Red（新函数还不存在时的类型 / 构建报错同样算）。禁止为了看到断言失败先写空实现。

### 4.3 失败基线

动手前在分支起点跑一次 P3 的 check，既有失败写进 PR 描述；没跑就沿用 P5 的常驻基线。此后「全绿」= 基线外
全绿。不建 `baseline.md`。

### 4.4 TDD 范围与豁免

**先写失败测试是默认**。计算、判定、状态流转、账务、鉴权、数据读写一律不豁免，哪怕只有三行。可以豁免的，
换成一个别的可跑检查：

| 情形 | 换成 |
|---|---|
| 纯展示（布局、文案、样式，无新逻辑分支） | 一张关键截图；A 车道按设计稿核对 |
| 配置 / 常量 / 注册（新增选项、注册路由、迁移列表） | 一条「注册后可读到」的冒烟测试或核对命令 |
| 纯文档 | 可执行清单 |

外部系统的 fixture 从真实响应录制（只读 key / testnet），不手写推测的格式与错误码。

### 4.5 三档的先行测试

核心不变量的测试在立项时写好（Red），随立项文件提交；实现方让它们转绿，**不改既有断言**——确需改（放松匹配、
删断言、跳过用例）的在 PR 描述里单列理由，合并前的审阅专门核对测试文件的 diff。只用于三档的单向门片。

## §5 Phase 完成协议（Phase Completion Verification and Checkpointing Protocol）

一个 phase 就是一片、一个 PR。phase 的最后一个任务完成后：

1. **check**：跑 P3 的 check 到全绿（基线外）；修两轮还不绿 → 断路器。
2. **证据**：check 输出；改了 UI 的附关键截图（A 车道按设计稿核对）。
3. **开 PR**（描述见 §5.1），同一分支上把本 phase 的 meta-task 勾成 `[x]`（含义：本片已交付，合并即上线）。
   track 的**最后一片**还要在这个 PR 里：tracks.md 该条目 → `[x]`；删掉后继条目的 `⛔ blocked_by` 前缀；
   按需同步 `conductor/product.md` / `tech-stack.md`（改动列在 PR 描述里）。
4. **审阅**：按 §6——三档的单向门片在这里审一次；一档有逻辑的审一次；其余不审。
5. **合并**：
   - 单向门片 → 用户合并（停点 4），先按 P2 跑 testnet / dry-run；
   - 其余 → 模型合并：`gh pr merge --squash --match-head-commit <完整 40 位 sha>`。auto 模式会把「模型合并自己的
     PR」判为自我批准拦下：用户在 `permissions.allow` 加了 `Bash(gh pr merge:*)` 才能由模型合并；没加就把合并命令
     交给用户并发通知，不要换写法绕过。
6. **上线**：`/flow:closeout`——按 P2 部署、冒烟、清理分支。
7. **请用户试**：发通知说去哪里点、会看到什么，**不等回复**，接着做下一片。用户的反馈改写后面的片。

conductor 原协议里的「等用户回复 yes」、检查点提交、`git notes`、检查点 SHA 回填一律不做。

**track 做完**（最后一片合并上线后）：按 §6 审一次整个 track，BLOCKER 立刻开修复片（代码已经在线上），然后汇报。

### 5.1 PR 描述

```
所属：<分诊卡一句 ｜ track <id> 第 N 片：<片目标>>
做了什么：<几条>
check：<命令与结果；基线外失败：无 ｜ 列出>
审阅：<VERDICT 行 ｜ 按 workflow §6 本片不审>
怎么试：<上线后去哪里点、看到什么；或一条命令>
已知未做：<这次不做的 / 留给下一片的>
```

## §6 审阅：一个改动审一次

顶级团队的做法：每个改动审一次，改动本身小；风险越高越靠审阅之外的保险（先行测试、testnet / dry-run、
负责人合并、上线冒烟与回滚），而不是多审几轮。

| | 一档 | 二档 | 三档 |
|---|---|---|---|
| 写代码前 | — | — | `flow:spec-reviewer` 审 spec 一次 |
| 每片合并前 | 有逻辑：`flow:phase-gate-reviewer` 1 次；纯展示 / 文案 / 配置：不审 | 不审，过 check 即合并 | 单向门片：`flow:phase-gate-reviewer` 1 次；其余片同二档 |
| track 做完 | — | `flow:phase-gate-reviewer` 1 次，看本 track 所有非展示片的 PR diff | 同二档，只看合并前没审过的非展示片；没有就不审 |

- **一次审阅派一个代理**，正确性、资金、安全、架构在同一次里看完；`flow:security-reviewer`、
  `flow:architecture-reviewer` 只在用户点名或审阅者建议时加派。
- **严重度按后果定**：可能导致重复下单、裸仓、资金 / 净值 / 记账错误、数据丢失、告警静默失败、密钥泄露、越权的，
  一律 BLOCKER，不管看起来多「不太可能」。
- **只有 BLOCKER 必须修。** 其余意见写进 PR 评论，作者自选；「测试没钉住」只有在三档核心不变量完全没有测试时
  才算 BLOCKER。不做变异分析，不审措辞与格式。
- **复审只核对 BLOCKER**，最多一次；复审后仍有 → 断路器。
- 审阅结论贴成 PR 评论，首行 `VERDICT: APPROVE | BLOCK`（`/flow:stats` 按这行计数）。track 做完的那次贴在最后一片的
  PR 上。
- 审阅者被要求找问题就总能找到——追每一条会导致过度工程。

## §7 收尾、记账与 conductor 覆盖声明

### 7.1 收尾（`/flow:closeout`，每片合并后立刻做）

部署（P2）→ 冒烟 → 清理（删远端分支、`git worktree remove`、`git branch -D`；叠链 PR 先 `gh pr edit --base <主干>`）
→ 主 checkout 拉到最新 → 请用户试。收尾不产生任何提交。

### 7.2 记账口径

- **状态真相源** = tracks.md 的 `[ ]` / `[~]` / `[x]` + plan.md 的复选框，只随代码提交改动：第一片的 PR 带上
  track 登记，最后一片的 PR 带上 `[x]`。
- tracks.md 每节前置一个 `---`（含首节），状态标记只许 `[ ]` / `[~]` / `[x]`（flow hook 校验）；superseded 用 `[x]` +
  描述行注明；想做但没立项的放 `conductor/backlog.md`。
- `metadata.json` 由 new-track 生成，之后不维护、不读取。
- **不做**：SHA 回填、`git notes`、检查点提交、`baseline.md`、phase 报告、HANDOFF、单独的记账或立项 PR。失败基线、
  审阅结论、交接都在 PR 描述与评论里；部署步骤变了才改 runbook。
- **产品决策**（改变规则、口径、资金模型的）写 `docs/decisions/<YYYY-MM-DD>-<slug>.md`，并同步修订上游设计文档。

### 7.3 conductor 覆盖声明（与本文件冲突时以本文件为准）

- **new-track**：分诊卡与访谈已经答过的不再问；还需要问的不超过 3 问，用 AskUserQuestion 一次问完，不逐个问。
  spec 与 plan 起草完**一起**给用户确认一次。track 文件写在第一片的 worktree 分支上。
- **implement**：每个任务按 §4，phase 末按 §5。track 完成后的文档同步（product.md / tech-stack.md /
  product-guidelines.md）写进最后一片的 PR、在描述里列出，不单独停下确认；完成后的归档 / 删除提示一律按「跳过」处理，不问。
  自动选题时跳过描述行以 `⛔ blocked_by` 开头、且前置 track 未 `[x]` 的条目。
- **setup**：由 `/flow:init` 编排（flow 的规则作为 workflow.md，不用 conductor 自带模板）。

## §8 教训、度量与分支

- **代码类教训**：能进 hook 的进 hook（`.claude/flow.json`；硬禁止用 `permissions.deny`）→ 只对某类文件成立的进
  `.claude/rules/`（frontmatter 用 `paths:`，写成 `globs:` 会被当成无条件规则）/ 领域陷阱进 skill → 最后才进 CLAUDE.md。
- **流程类教训**：用户对流程不满或流程出了错 → **当天改本文件**：所有项目适用的提到 flow 插件仓库发版，只属于本
  项目的写进「项目补充」。memory 只留指针——写在 memory 里的流程规则，别的 session 和 agent 看不到，等于没改。
- **度量**：定期跑 `/flow:stats`。目标：双向门的片当天上线；PR 中位数非测试代码 ≤400 行；每个改动审阅 ≤1 次；
  只改文档的提交 <15%。感觉不可靠，看数。
- **分支**：主 checkout 只读，永远停在主干，一切改动走 worktree（flow 的 hook 会拦）；动手前 `git fetch`，查有没有
  既有分支或已合并 PR 在做同一件事。提交用 conventional commit：`<type>(<scope>): <description>`，type ∈ feat / fix /
  docs / refactor / test / chore，描述用英文。
- **改项目自己的 hook / settings.json**：它们锚定 session 启动目录，worktree 分支上的改动合并前不生效——在分支上
  手工喂 stdin JSON 验证（正例 + 反例），合并后第一个 session 复验。
