一档（小而明确）需求的**全流程**：一页规格 → 实现 → 验收 → PR。目标是**一个 session、一个 PR**。

不适用（升二/三档，开 track）：跨 ≥2 层（按 workflow.md P2 数）、涉 P1 敏感域、改既有表列、
改已上线口径、需要多 phase 才说得清。

## 1. 访谈（条件式，最多 3 问）

**用户已经说清的不要问。** 只问「不问就会做错、且答案会改变实现」的点，用 AskUserQuestion 一次性
问完（≤3 题）。典型该问的：happy path 的关键分支、失败/并发时的期望行为、明确不做什么。
典型不该问的：用什么框架、要不要写测试、命名偏好——这些照仓库现有模式来。

问不出实质分歧就直接进第 2 步，不要为了"走流程"凑问题。

## 2. 代码调研（用 subagent，别占主上下文）

派一个 Explore/general-purpose subagent 摸清：现有实现在哪、可复用的模式与 helper、会被影响的
调用方、既有测试怎么写的。让它返回结论与 `file:line`，不要返回大段代码。

## 3. 写规格：`docs/specs/<功能名>.md`（一页，DELTA 形态）

```markdown
# <功能名>

> 状态: 进行中 ｜ 档位: 一档 ｜ 日期: YYYY-MM-DD

## 目标
<一段话：谁在什么场景下做什么，期望什么结果>

## 现状 → 目标行为
| | 现状 | 目标 |
|---|---|---|
| ... | ... | ... |

## 明确不改
- <边界清单：哪些文件/行为这次不动。review 和验收拿它当边界>

## 验收标准（每条配一条可跑的检查）
- [ ] AC1 …… — `<测试命令，精确到用例>`
- [ ] AC2 …… — `<测试命令>`
- [ ] AC3（涉 UI）…… — 截图矩阵（workflow.md P4）

## 做完用户能用到什么
<一句话，用用户的语言，不是技术语言>

## 参考的现有模式
- `path/file:123` — 参考了什么
```

**不留"待定事项"**：用户可见文案、账务公式、API 契约必须逐字确定；内部实现细节写
「实现方自选」而不是「待定」。

## 4. 实现

- worktree 里做（主 checkout 只读）；动手前在分支起点跑一次相关测试，记下失败基线（workflow §4.3）
- TDD：先写失败测试再实现（Red 判定见 workflow §4.2）
- 提交用 conventional commit，描述英文

## 5. 出口门禁（必须做完再开 PR）

1. AC 里的命令**逐条跑过**，贴结果
2. **1 次 code review agent**：输入 = diff + 本规格的 AC 与「明确不改」清单；只报影响正确性或
   AC 缺口的问题，风格意见不算（workflow §5 同款口径）。MAJOR 修完再开 PR，MINOR 可选
3. 涉 UI：附截图矩阵（workflow.md P4，默认 light/dark × 375/1280）
4. 规格头部状态改 `已合并 PR #n`（合并后回填），别让 `docs/specs/` 留一堆"进行中"

## 6. 汇报（三行，workflow §3.3 格式）

```
现在能用什么：…
还缺什么：…
需要你做什么：…（一档通常只有「合并 PR」）
```
