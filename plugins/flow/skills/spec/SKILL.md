一档（小而明确）需求的全流程：一页规格 → 实现 → check → PR → 上线。目标是**一个会话、一个 PR**。

不适用（改档开 track）：要多片才做得完；碰 P1 单向门（动钱、记账口径、密钥权限、改既有表列 / 数据迁移、审批守卫）；
视觉没定要设计包。做着发现属于这些 → 停下改档，不硬塞进一个 PR。

## 1. 访谈（条件式，最多 3 问）

分诊卡已经答过的不再问。只问「不问就会做错、且答案会改变实现」的点，用 AskUserQuestion 一次问完。典型该问的：
happy path 的关键分支、失败 / 并发时的期望、明确不做什么。用什么框架、要不要写测试、命名照仓库现有模式来，不问。
问不出实质分歧就直接进第 2 步。

## 2. 代码调研（用 subagent，别占主上下文）

派一个 Explore subagent 摸清：现有实现在哪、可复用的模式与 helper、会被影响的调用方、既有测试怎么写。只要结论与
`file:line`。能看真实数据（只读）就一起看。

## 3. 写规格：`docs/specs/<功能名>.md`（一页，DELTA 形态）

```markdown
# <功能名>

> 状态: 进行中 ｜ 档位: 一档 ｜ 日期: YYYY-MM-DD

## 目标
<一段话：谁在什么场景下做什么，期望什么结果>

## 现状 → 目标行为
| | 现状 | 目标 |
|---|---|---|

## 明确不改
- <这次不动的文件 / 行为；审阅和验收拿它当边界>

## 验收标准（每条配一条可跑的检查）
- [ ] AC1 …… — `<测试命令，精确到用例>`
- [ ] AC2（涉 UI）…… — 截图

## 做完用户能用到什么
<一句话，用户的语言>
```

用户可见文案、资金公式、对外契约逐字确定；实现细节写「实现方自选」，不写「待定」。纯文案 / 样式 / 配置的小改动
可以不写规格文件，分诊卡 + PR 描述就够。

## 4. 实现

- worktree 里做（主 checkout 只读）；动手前在分支起点跑一次 P3 的 check，记下既有失败（workflow §4.3）。
- 先写失败测试再实现（workflow §4.2 / §4.4）；外部系统的 fixture 从真实响应录制。
- conventional commit，描述用英文。

## 5. 出口

1. P3 的 check 跑到全绿（基线外），AC 命令逐条跑过；改了 UI 的附一张关键截图。
2. **审阅（workflow §6）**：有逻辑（计算、判定、状态、数据读写）→ 派 `flow:phase-gate-reviewer` 审一次这个 PR；
   纯展示 / 文案 / 配置 → 不审。只有 BLOCKER 必须修，复审只核对 BLOCKER、最多一次。结论贴成 PR 评论。
3. 开 PR，描述按 workflow §5.1；规格头部状态改成 `PR #n`。
4. 合并（workflow §5 第 5 步：有 `Bash(gh pr merge:*)` 权限由模型合并，否则把命令交给用户并发通知）→
   `/flow:closeout` 上线、请用户试。

## 6. 汇报（三行，workflow §1）

```
现在能用什么：…
还缺什么：…
需要你做什么：…（去哪里试 ｜ 合并 PR #n ｜ 无）
```
