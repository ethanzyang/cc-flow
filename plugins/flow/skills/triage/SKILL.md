把需求路由到**右尺寸**的流程。输出一张分诊卡（≤10 行），等用户一句话确认或否决，然后按选定档位
执行。不要跳过分诊直接开工，也不要为了分诊问一堆问题——分诊本身最多 1 问。

先读 `conductor/workflow.md` 的 §2 与文末 **P1（敏感域）/ P2（层划分）**——判档要用本项目的定义。
没有 `conductor/workflow.md` → 本仓库还没接入 flow，提示用户先跑 `/flow:init`。

## 步骤

### 1. 复述需求（一句话，用用户的语言）

用**用户能验收的说法**复述，不要用技术分解。例：「一个能发给别人的安装入口 + 知道谁从哪来 +
排错文档」。

### 2. 判档（workflow §2.1）

| 问 | 答 | 档 |
|---|---|---|
| 碰 P1 列出的敏感域？改既有表列？改已上线口径？跨仓契约？视觉不确定？ | 任一是 | **三档** |
| 跨 ≥2 层（按 P2 数）或需要多个 phase？ | 是 | **二档** |
| 都不是，一段话说得清 | | **一档** |

**文件数不作判据。** schema 只要是纯新增表/索引，不影响档位。

### 3. 判车道（workflow §2.2）

不确定性在「长什么样才对」→ Lane A；在「怎么改才对」→ Lane B/C；没有 → Lane D 直接修。

**新页面不等于 Lane A。** 三条同时满足就降级为 Lane B（workflow §3.1）：只用既有 token 与既有组件
语法、无新交互模式、结构与文案能在 spec 里逐字给出。降级要在卡里写明理由。

### 4. 拆分判断（workflow §2.3）

只有需求明显含两块不同性质的工作时才考虑拆。**拆之前必须答**：

> 做完第一段，用户能亲手用到什么？

答不出、或答案里没有需求原话的主入口 → **不拆**，一个 track 分 phase。
决定拆 → 两段**同时立项**（都进 tracks.md，后段 `blocked_by`），第二段免重走采访。

### 5. 输出分诊卡

```
需求：<一句话复述>
档位：<一/二/三档> — <判据，一句话>
车道：<A/B/C/D>（新页面降级理由：…）
拆分：<不拆，分 N 个 phase ｜ 拆 2 段，同时立项，第一段交付 X>
做完用户能用到什么：<一句话>
本次流程：<入口命令 / 产物 / session 数 / review 次数 / 验收方式>
本次允许的停点：<从 workflow §0 的 5 处里列出这次会用到的>
```

给用户看这张卡，**等一句确认**（可以是「行」「按这个做」）。用户否决某一项就改那一项，不重来。

### 6. 执行

- 一档 → `/flow:spec`
- 二/三档 → `/conductor:new-track`（Lane A 先设计 → `/flow:design-track`）
- Lane D → 直接修（复现测试 → 修 → 回归）

动手前先 `git fetch`，查有没有既有分支或已合并 PR 在做同一件事；改动一律在 worktree 里做
（主 checkout 只读，flow hook 会拦）。

确认后**不再回来问流程问题**；后续所有决策点按 workflow §0 由 review agent 代拍板。
