把需求路由到**右尺寸**的流程，用最少的来回让用户和模型对「做什么、做多大、怎么算做完」达成一致。
**这一步不写代码、不开分支、不立项。**

先读 `conductor/workflow.md` 的 §0–§3 与文末 **P1（单向门清单）/ P2（上线）/ P4（UI 与设计输入）**。
没有 `conductor/workflow.md` → 本仓库还没接入 flow，提示用户先跑 `/flow:init`。

## 1. 弄清目的

- 用**用户能验收的说法**复述需求，一句话，不做技术分解。
- 先从产品角度想清楚三件事：这件事背后的目的、谁在操作（用户手动 / 系统按规则）、系统该为它承担什么。
  不要为了让现状能跑而补症状，也不要拿现有代码的做法收窄用户的需求。
- **能看真实数据就先看**（只读）：用户的真实账户、真实接口返回、线上日志与数据库，比推测可靠。代码调研派一个
  Explore subagent，只要结论与 `file:line`，不要大段代码。
- 用户只是在问「怎么办 / 我要方案」（讨论模式，workflow §0）：给 1–2 个方案和推荐，以分诊卡收尾，**等用户说「做」**。

## 2. 判档（workflow §2.1）

| 问 | 答 | 档 |
|---|---|---|
| 这次改动错了，revert 重新部署能不能就没事？（对照 P1，拿不准按「不能」） | 不能 | **三档** |
| 一个 PR（非测试代码约 400 行）做不做得完？ | 做不完 | **二档** |
| | 做得完 | **一档** |

层数、文件数不作判据；纯新增表 / 索引不升档。三档 track 里，「钱怎么动」和「页面怎么显示」切成不同的片，
后者按二档走。

## 3. 判车道与设计输入（workflow §2.2、§3.2）

- 不确定性在「长什么样才对」→ A；在「怎么改才对」→ B（行为变）/ C（重构）；都没有、单点缺陷 → D 直接修。
- 有用户可见界面时必判设计输入：

| 情况 | 设计输入 |
|---|---|
| 新界面 / 新交互，视觉没定 | **设计包**：`/flow:design-track` 在立项里出（设计先行；行为也要收敛的 → 行为片在前，UI 片前再出设计包） |
| 新页面，满足降级三条（只用既有 token 与组件语法、无新交互模式、结构与文案能逐字写进 spec） | spec 内嵌结构清单 + 逐字文案 + 状态，卡上写明降级理由 |
| 改既有界面的样式 / 布局 | 动手前截现状 |
| 纯后端 | 无 |

**视觉没定不升档**——它决定走不走设计环节，不决定档位。

## 4. 定胃口、切片（workflow §2.3、§3.1）

- **胃口** = 这件事值得花多少时间（1 小时 / 半天 / 一天），不是估算；超出胃口就砍范围。
- **切成竖切小片**：每片端到端可用、能单独上线、非测试代码约 400 行以内。第一片要最小、最快让用户用上；
  新能力的第一片先打通真实外部系统。后面的片可以写「等用户用过第一片再定」。
- **拆成两个 track** 只在需求里有两块能各自交付的东西时考虑。拆之前必须答「做完第一段，用户能亲手用到什么」，
  答不出就不拆；拆了就同时立项（后段 `⛔ blocked_by`）。

## 5. 访谈（可选，最多 3 问，workflow §1 停点 2）

只问「不问就会做错、且答案会改变实现」的点，**AskUserQuestion 一次问完**。用户说过的不问；显而易见的不问
（用什么框架、要不要写测试、命名，照仓库现有模式来）；流程问题不问（开不开新 session、用哪个 skill 由模型定）。
问不出实质分歧就不问，不要为了走流程凑问题。

## 6. 输出分诊卡（≤12 行）

```
需求：<一句话复述，用户的语言>
档位：<一 / 二 / 三档> — <门：双向 ｜ 单向（P1 哪一类）；规模：一个 PR ｜ N 片>
车道：<A / B / C / D>；设计输入：<设计包 ｜ spec 内嵌结构（降级理由）｜ 现状截图 ｜ 无>
第一片做完你能：<一句话，用户能亲手做到的事>
切片：<1. … 2. … 3. …（后面的可以等用过第一片再定）>
这次不做：<…>
胃口：<…>
怎么验收：<上线后在哪里点、看到什么；或一条命令>
本次流程：<入口；审阅几次（workflow §6）；哪一片要你合并>
```

给用户看这张卡，**等一句「做」**。用户否决某一项就只改那一项，不重来。用户不在（无人值守）→ 模型按卡拍板，
把假设写进 PR 描述，直接执行。

## 7. 执行

动手前先 `git fetch`，查有没有既有分支或已合并 PR 在做同一件事；改动一律在 worktree 里做（主 checkout 只读，
flow 的 hook 会拦）。

- **一档** → `/flow:spec`（D 车道直接修：复现测试 → 修 → 回归，同样一个 PR）。
- **二 / 三档** → 立项一个 track，track 文件提交在第一片的分支上（workflow §3.1）：
  - 设计包 · 设计先行 → 从 `/flow:design-track <feature>` 开始：先把 BRIEF 推到用户的 Claude Design 让用户画，
    画完再跑一次，拉回设计包、快照进新 track，接着出 spec / plan；
  - 设计包 · 行为先冻结 → `/conductor:new-track` 先立行为；plan 里 UI 片的第一个任务写成
    「`/flow:design-track <feature> --track <本 track>`」；
  - 其余 → `/conductor:new-track`，把分诊卡整张作为它的描述传进去，并说明「分诊卡与访谈已答的不再问
    （workflow §7.3）」。
  - 三档：spec 写完派 `flow:spec-reviewer` 审一次，BLOCKER 修进 spec；plan 里每个单向门片的第一个任务是「提交先行测试
    （立项上下文完成）」，测试提交在那一片自己的分支上，不随第一片合并（§4.5）。
  - spec + plan 一起给用户确认一次（停点 3）。确认后：二档在本会话直接 `/conductor:implement`；三档换干净
    上下文开工——新 session 开在第一片的 worktree 里（或先 `/flow:catchup`），或派一个只拿 spec / plan 的新 agent。

确认后**不再回来问流程问题**；其余决策按 workflow §1 由模型拍板，理由写进 PR 描述。
