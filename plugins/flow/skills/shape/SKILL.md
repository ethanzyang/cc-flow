---
name: shape
description: 定形——把一个需求（或用户的困惑）收敛成一张 ≤15 行的定形卡：目标、第一片做完用户能做什么、这次不做、胃口、单向门还是双向门、怎么验收、切片。拿到任何新需求先跑它；用户说「怎么做」「我要方案」「先研究」「分诊」「这个要多久」时也触发。规则见 conductor/workflow.md §1–§3.1。
---

目标：用最少的来回，让用户和模型对「这次做什么、做多大、怎么算做完」达成一致。**这一步不写代码、
不开分支、不写 spec。**

先读 `conductor/workflow.md` 的 §1–§3 与文末 **P1（单向门清单）/ P2（上线）**。没有 workflow.md →
本仓库还没接入 flow，提示用户先跑 `/flow:init`。

## 1. 弄清目的（讨论模式）

- 用用户的语言复述需求，一句话。
- 想清楚三件事再给方案：这件事背后的目的是什么、谁在操作（用户手动 / 系统按规则）、系统该为它承担什么。
  先从产品角度想，不要为了让现状能跑而补症状。
- **看真实数据**（只读）：用户的真实账户、真实接口返回、线上日志与数据库——比推测可靠。代码调研派一个
  Explore subagent，只要结论与 `file:line`。
- 用户只是在问「怎么办」时，到这里给出 1–2 个方案与推荐，以定形卡收尾，**等用户说「做」**。

## 2. 判门（workflow §2）

问一句：这次改动错了，revert 重新部署能不能就没事？不能 → 单向门（对照 P1）；能 → 双向门。拿不准按单向门。
不按层数、文件数判。

## 3. 定胃口、切片（workflow §3.2）

- 胃口 = 这件事值得花多少时间（1 小时 / 半天 / 一天），不是估算。超出胃口就砍范围。
- 切成竖切小片：每片端到端可用、能单独上线、非测试代码约 ≤400 行。第一片要最小、最快让用户用上；
  新能力的第一片先打通真实外部系统。后面的片可以写「等用户用过第一片再定」。
- 单向门里「钱怎么动」和「怎么显示」拆开，后者通常是双向门。

## 4. 提问（可选，最多 3 问）

只问「不问就会做错、且答案会改变实现」的点，AskUserQuestion 一次问完。用户说过的不问；显而易见的不问；
流程问题不问（用哪个 skill、开不开新 session 由模型决定）。

## 5. 输出定形卡

```
目标：<用户原话>
第一片做完你能：<一句话，用户能亲手做到的事>
这次不做：<…>
胃口：<…>
门：双向 ｜ 单向（<P1 哪一类>）
怎么验收：<上线后在哪里点、看到什么；或一条命令>
切片：<1. … 2. … 3. …>
```

用户说「做」/「行」→ 第一片交给 `/flow:build`（单向门先写 spec 并过 `flow:risk-reviewer`，见 workflow §4）。
用户改某一项就只改那一项。用户不在（无人值守）→ 模型拍板，把假设写进 PR 描述，直接进 build。
